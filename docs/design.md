## Problem Statement

Full-stack developer works across two machines: a remote server (no GUI, internal network access to k8s) for backend, and a local machine (with GUI browser) for frontend. During frontend-backend integration testing, two separate Claude Code instances run independently on each machine. The developer is the "human bridge" — manually deploying backend changes, switching to the local machine, re-explaining context to local Claude Code, and testing in the browser.

The core workflow today:
1. Server Claude Code modifies an API
2. Developer manually deploys to k8s
3. Developer switches to local machine, opens browser
4. Developer walks through authentication flow
5. Developer hands browser to local Claude Code (or tests manually)
6. Local Claude Code has zero context about what changed on the server

This loop repeats many times per day during integration testing.

## What Makes This Cool

This is the first tool that enables E2E encrypted, cross-machine AI-to-AI collaboration. Not just message passing — shared cognitive context between two Claude Code instances that can't see each other's filesystem.

Key innovations:
- **Delegation with context**: Server Claude sends structured work orders (API diff + schema + what to test), local Claude acts autonomously
- **Shared context layer**: Both Claude instances maintain a synchronized key-value context store (API diffs, schema changes, deploy status) — not a full "mental model," but a concrete, queryable record of what changed
- **Real-time message delivery**: WebSocket delivers messages to the bridge client instantly. Note: triggering Claude Code to act on incoming messages requires either Claude Code hooks or a wrapper process (see Task Trigger Mechanism below)
- **Zero-knowledge relay**: Cloudflare sees encrypted blobs, never the content
- **MCP-native integration**: Claude Code talks to the bridge through its existing MCP tool system

## Constraints

- E2E encryption is non-negotiable (TweetNaCl: X25519 key exchange + XSalsa20-Poly1305)
- Cloudflare Workers + Durable Objects as relay platform
- Must work across network boundaries (internal server ↔ public internet ↔ local machine)
- Both task dispatch and free-form conversation supported
- Architecture must support future public service scenario
- No GUI required on the server side

## Premises

1. Two Claude Code instances on different machines need bidirectional communication (task dispatch + free conversation), and no existing solution (Agent Teams, Remote Control, MCP) covers cross-machine
2. E2E encryption is required — Cloudflare relay must not decrypt message content
3. Cloudflare is the relay platform (cheap, serverless, potential public service)
4. Primarily solving own pain (full-stack dev integration testing), but architecture should support public service
5. Cost of inaction: continue being the human bridge, manually deploying, switching contexts, re-explaining

## Cross-Model Perspective

Claude subagent provided independent analysis:

- **Coolest version**: Shared cognitive context with session replay — a distributed scratchpad where both Claudes maintain a synchronized mental model, with the ability to replay cross-machine debugging sessions
- **Key insight**: The user doesn't want a chat system. They want "delegation with context" — one AI acting as project lead dispatching work with enough context for the other to act autonomously

## Approaches Considered

### Approach A: Minimal Bridge
Cloudflare Worker as pure relay. Two MCP servers (one per machine) expose send/receive tools. TweetNaCl E2E encryption. Claude Code calls MCP tools to communicate.

- Effort: S
- Risk: Low
- Pros: Fastest to ship, leverages existing MCP ecosystem, simple architecture
- Cons: Polling only (MCP is client-initiated), no shared context, no task lifecycle, messages are fire-and-forget

### Approach B: Context-Aware Bridge (CHOSEN)
Approach A + Durable Object for persistent state. Shared context layer (API diffs, schema changes, deploy status) auto-syncs. WebSocket real-time push. MCP server + WebSocket listener on each end.

- Effort: M
- Risk: Medium
- Pros: Real-time message delivery, shared context, task lifecycle (pending → ack → in_progress → done/failed), clean architecture for future public service
- Cons: Durable Object state management adds complexity, WebSocket + MCP dual integration

### Approach C: Distributed AI Trace
Approach B + session replay, debug timeline, multi-party support. Full public service features (auth, billing, multi-tenant).

- Effort: L-XL
- Risk: High
- Pros: Unique value proposition, real product potential, session replay is genuinely novel
- Cons: High complexity, scope creep risk, far from "solve my own pain"

## Recommended Approach

**Approach B: Context-Aware Bridge.** It solves the real pain (real-time push + shared context for frontend-backend integration) while keeping the architecture clean enough to extend into a public service later.

### Architecture

### Component Breakdown

**1. Cloudflare Worker + Durable Object (Relay)**
- Worker handles HTTP endpoints for room creation, key exchange bootstrap
- Durable Object per bridge session: WebSocket hub, stores encrypted message history
- Zero knowledge: all payloads are pre-encrypted blobs
- Room lifecycle: create → join → active → idle timeout → cleanup
- Simple room code system for pairing (e.g., 6-char alphanumeric)

**2. Bridge Process (Node.js / TypeScript) — single process, two roles**

The bridge client and MCP server run as a **single Node.js process**. The process has two interfaces:
- **Outward**: WebSocket connection to Cloudflare DO (encrypted relay)
- **Inward**: MCP stdio transport for Claude Code integration

This single-process design avoids IPC complexity. The process manages:
- WebSocket connection to Cloudflare DO
- TweetNaCl encryption/decryption layer
- Key management: generates X25519 keypair, exchanges public keys through relay
- MCP tool handlers (see below)
- Incoming message queue for WebSocket push events

**MCP Tools exposed to Claude Code:**
- `bridge_send_message(content)` — send encrypted message to peer
- `bridge_send_task(description, context, priority)` — dispatch a task with structured context
- `bridge_get_messages(since?)` — read recent messages from incoming queue
- `bridge_get_tasks(status?)` — list tasks by status
- `bridge_update_task(id, status, result?)` — update task status (pending → ack → in_progress → done/failed)
- `bridge_get_context()` — read shared context key-value store
- `bridge_set_context(key, value)` — write to shared context key-value store

**3. Task Trigger Mechanism (Critical Design Decision)**

MCP is client-initiated — Claude Code calls tools, tools don't call Claude Code. When a task arrives via WebSocket, how does local Claude Code know?

**Primary approach: Claude Code hooks**
Claude Code supports pre/post hooks on tool calls and user prompt submissions. Configure a hook that checks for pending bridge tasks on each Claude Code interaction. This piggybacks on existing Claude Code activity — not true push, but low-latency for active sessions.

**Fallback approach: Bridge watcher process**
A separate `claude-bridge watch` process polls the local bridge for incoming tasks every 5 seconds. When a task arrives, it invokes `claude-code --print "You have a new bridge task: [task description]"` to spawn a new Claude Code session. This works even when no Claude Code session is active.

**For MVP**: Start with the watcher approach — it's simpler, more reliable, and doesn't depend on hook API stability. Add hook integration later for tighter UX.

**4. Message Protocol**
```typescript
type BridgeMessage = {
  id: string;              // UUID
  protocolVersion: 1;      // increment on breaking changes; reject connection on mismatch
  type: 'task' | 'context' | 'result' | 'chat';
  from: string;            // peer identity (public key fingerprint)
  timestamp: number;
  payload: TaskPayload | ContextPayload | ResultPayload | ChatPayload;
};

// Max message size: 256KB before encryption. Enforced at bridge client.
// Cloudflare limits: 1MB WebSocket frame, 128MB DO storage.

type TaskPayload = {
  description: string;     // what to do
  context: string;         // API diff, schema change, etc.
  priority: 'low' | 'normal' | 'high';
};

type ContextPayload = {
  key: string;             // e.g., "api_diff", "deploy_status"
  value: string;
  operation: 'set' | 'append' | 'delete';
  // Conflict resolution: last-write-wins by timestamp.
  // For MVP, peers typically own different keys. If both write the same key,
  // the message with the later timestamp takes precedence.
};

type ResultPayload = {
  taskId: string;          // references the original TaskPayload
  status: 'ack' | 'in_progress' | 'done' | 'failed';  // covers full lifecycle
  summary?: string;        // required for done/failed, optional for ack/in_progress
  details?: string;        // full output, logs, screenshots, etc.
};

type ChatPayload = {
  content: string;         // free-form text message
  replyTo?: string;        // optional: message ID being replied to
};
```

**5. Encryption Flow**

Room metadata is unencrypted state stored in the Durable Object, containing only: room code, peer public keys, room creation timestamp, and room status. This is the only data the relay can read.

1. Host creates room → generates X25519 keypair → publishes public key to room metadata
2. Joiner joins room → generates X25519 keypair → reads host's public key → publishes own public key
3. Both compute shared secret via X25519 Diffie-Hellman
4. All subsequent messages encrypted with XSalsa20-Poly1305 using shared secret
5. Relay (Durable Object) only ever sees encrypted blobs + room metadata

**6. Key Exchange Security**
- Public keys exchanged through the Cloudflare relay (acceptable for personal use)
- Room codes are short-lived and single-use
- Future enhancement: out-of-band verification (QR code, fingerprint comparison) for higher security
- Future enhancement: key rotation on reconnection (new keypairs, re-exchange, grace period for in-flight messages encrypted with old key). Not in MVP — the shared secret persists for the session lifetime.

**7. Task State Tracking**

Important: the DO cannot read encrypted message content. All task state is tracked **locally by each bridge client**, not by the DO. The DO is a dumb pipe for encrypted blobs.

- Each bridge client maintains a local task table (in-memory + optional file persistence)
- Task status updates are communicated via `result`-type BridgeMessages between peers
- Task lifecycle: A sends `task` message (local status: pending) → B receives, sends `result` message with status `ack` → A updates local status to `ack` → B starts working, sends `result` with status `in_progress` → B finishes, sends `result` with status `done`/`failed` + summary → A updates local status accordingly

**8. Failure Modes**
- **WebSocket disconnect during task**: Task stays in local `in_progress` state. On reconnection, bridge client requests message replay from DO (see delivery guarantee below). If no status update arrives within 5 minutes of reconnection, sender client marks task as `failed` locally.
- **Peer goes offline**: Messages queue in Durable Object (encrypted blobs). When peer reconnects, queued messages are delivered. TTL: 24 hours, then auto-deleted.
- **Task dispatched but never acknowledged**: After 60 seconds with no `ack` message from receiver, sender client marks task as `failed` locally with reason "no acknowledgment." Sender Claude Code sees this via `bridge_get_tasks`.
- **Durable Object eviction**: DOs can be evicted after inactivity. State is persisted to DO storage, so reconnection restores state. WebSocket must be re-established.
- **Message delivery guarantee**: At-least-once delivery. On WebSocket reconnect, the bridge client sends a `sync` request with the ID of the last message it received. The DO replays all messages after that ID. Receivers deduplicate by message ID using a local set of seen IDs (bounded to last 1000 messages). No exactly-once guarantee (complexity not worth it for this use case).

**9. Cost Estimate**
Assuming moderate personal use: ~200 messages/day, ~5KB average per encrypted message.
- Storage: ~1MB/day, ~30MB/month — well within Durable Object included storage (1GB free)
- Requests: ~400 WebSocket messages/day (send + receive) — well within Workers free tier (100K requests/day)
- DO duration: ~8 hours active/day — ~$0.15/month at $0.50/million duration-charged requests
- **Total estimated cost: < $1/month for personal use**

### Build Sequence

**Phase 1: Core Relay + Encryption (Day 1-2)**
- Cloudflare Worker + Durable Object with WebSocket
- Room create/join flow with room codes
- TweetNaCl X25519 key exchange + XSalsa20-Poly1305 encryption from day one
- Note: Encryption is non-negotiable. Even during local development, all messages go through the encrypt/decrypt path to catch integration issues early.

**Phase 2: MCP Integration (Day 2-3)**
- MCP server with bridge tools
- Claude Code config for MCP server registration
- Basic send/receive flow working end-to-end

**Phase 3: Task Trigger + Watcher (Day 3-4)**
- `claude-bridge watch` process: polls for incoming tasks, spawns Claude Code sessions
- Structured message types (task, context, result, chat)
- Task lifecycle management (pending → ack → in_progress → done/failed)
- Context sync key-value store

**Phase 4: Polish + CLI (Day 4-6)**
- CLI commands: `claude-bridge host`, `claude-bridge join <code>`, `claude-bridge status`, `claude-bridge watch`
- Reconnection logic with state re-sync from DO
- Graceful shutdown
- Error handling: task timeouts, connection loss recovery, message deduplication
- Logging with structured output

**Phase 5: Validation (Day 6-7)**
- End-to-end test across two machines
- Encryption round-trip verification
- Demo flow: server sends API change task → local Claude Code receives and acts

### Tech Stack

- **Relay**: Cloudflare Workers + Durable Objects (TypeScript, Wrangler)
- **Client**: Node.js / TypeScript
- **Encryption**: tweetnacl (or tweetnacl-ts)
- **MCP**: @modelcontextprotocol/sdk
- **CLI**: commander or yargs
- **No frameworks**: Zero frontend frameworks, zero ORMs, zero build tools beyond Wrangler

## Open Questions

1. **Multi-session**: Should the bridge support multiple concurrent rooms per user, or 1:1 only for MVP? (Recommendation: 1:1 for MVP)
2. **Authentication for public service**: When this becomes a public service, how to authenticate users? Cloudflare Access? API keys? OAuth? (Deferred to post-MVP)
3. **Rate limiting**: What limits are appropriate for the free tier of a public service? (Deferred to post-MVP)
4. **File transfer**: Should the bridge support sending files (screenshots, diffs as files) or only text? (Recommendation: text-only for MVP, files as future enhancement)

## Success Criteria

1. Server Claude Code sends a task → message arrives at local bridge client within 2 seconds (network latency). Local Claude Code begins acting on the task within ~30 seconds (5s watcher poll interval + up to ~25s Claude Code `--print` startup)
2. Two Claude Code instances can have a free-form conversation across machines
3. All messages are E2E encrypted — intercepting Cloudflare traffic reveals nothing
4. Setup takes < 5 minutes per machine (npm install + config)
5. Works reliably across NAT, firewalls, and corporate networks (WebSocket through HTTPS)

## Testing Strategy

- **Unit tests**: Encryption round-trip (encrypt → decrypt → verify plaintext match), message serialization/deserialization, room code generation uniqueness
- **Integration tests**: Two local bridge instances connecting through a local Cloudflare dev server (`wrangler dev`), full key exchange + encrypted message send/receive
- **Manual E2E checklist**: Two separate machines, create room on machine A, join on machine B, send task from A, verify B receives and can act on it, verify Cloudflare logs show only encrypted blobs
- **Security smoke test**: Intercept WebSocket traffic with a proxy, verify all payloads are opaque encrypted data
